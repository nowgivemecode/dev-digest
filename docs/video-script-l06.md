# Відео-скрипт: ДЗ L06 — Eval Pipeline (~3–5 хв)

## Підготовка ДО запису (не показувати на камеру)

1. `./scripts/dev.sh` — запустити весь стек
2. Відкрити DevDigest у браузері → переконатись що є хоча б 1 агент
3. Відкрити будь-який PR у якому вже є знайдення (findings) з accept/dismiss

---

## ЧАСТИНА 1 — Створення eval case зі знахідки

**Де:** PR → вкладка Findings

**Дії:**
1. Відкрити PR з вже запущеним review
2. Знайти finding з вердиктом **accepted** або **dismissed**
3. Натиснути кнопку **🧪 Turn into eval case**
4. Toast: "Eval case created"
5. Повторити для ще 1–2 findings

**Що говорити:**
> "Я завершив реалізацію eval pipeline. Починаємо зі створення тест-кейса.
> Ось знахідка від агента — я її прийняв як корректну. Тиснемо нову кнопку
> 'Turn into eval case' — вона з'явилась для accepted і dismissed знахідок.
> Це створює кейс типу must_find — агент повинен знайти саме це місце.
> Зробимо ще один із dismissed знахідки — це буде must_not_flag,
> тобто агент не повинен сюди чіплятись."

---

## ЧАСТИНА 2 — Запуск прогону, метрики

**Де:** Agents → агент → вкладка **Evals**

**Дії:**
1. Відкрити AgentEditor → вкладка **Evals**
2. Показати список eval cases
3. Натиснути **Run all evals**
4. Почекати завершення → показати метрики

**Що говорити:**
> "Переходимо в AgentEditor — тут з'явилась нова вкладка Evals.
> Бачимо список кейсів що щойно створили.
> Тиснемо 'Run all evals' — система запускає reviewer-core на кожному кейсі,
> але scoring — це чистий TypeScript, жодного LLM-у в підрахунку метрик.
> Після завершення бачимо: Recall, Precision, Citation Accuracy.
> Це перший baseline — запам'ятаємо ці цифри."

---

## ЧАСТИНА 3 — Змінюємо промпт, другий прогін

**Де:** AgentEditor → вкладка Config → потім знову Evals

**Дії:**
1. Вкладка **Config** → у system prompt дописати рядок:
   ```
   Flag unused imports as suggestions.
   ```
2. Натиснути **Save agent**
3. Повернутись на вкладку **Evals** → **Run all evals** (другий раз)
4. Показати нові метрики

**Що говорити:**
> "Тепер змінимо систем промпт — додамо одне нове правило.
> Зберігаємо агента — версія збільшилась.
> Запускаємо eval ще раз. Ідея в тому, щоб побачити як зміна промпту
> впливає на якість — це і є regression harness."

---

## ЧАСТИНА 4 — Eval Dashboard, порівняння двох прогонів

**Де:** sidebar → **Eval Dashboard** → `/evals/[agentId]`

**Дії:**
1. Sidebar → **Eval Dashboard**
2. Клік по картці агента → `/evals/[agentId]`
3. Відмітити чекбокси двох runs у таблиці
4. Натиснути **Compare**
5. Показати модал: дельти метрик + diff системного промпту

**Що говорити:**
> "Переходимо в Eval Dashboard — тут видно всіх агентів і їх runs.
> Клікаємо по нашому агенту — бачимо trend chart по метриках
> і таблицю запусків.
> Відмічаємо два прогони і тиснемо Compare.
> Бачимо: як змінились Recall, Precision, Citation між запусками,
> і точно який рядок ми додали в промпт.
> Це дозволяє зрозуміти — чи зробила зміна промпту агента кращим чи гіршим,
> без ручної перевірки кожної знахідки."

---

## Порядок: 1 → 2 → 3 → 4

| Критерій з ДЗ | Де видно у відео |
|---|---|
| Створення кейса зі знахідки | Частина 1 |
| Перший прогін → метрики | Частина 2 |
| Другий прогін зі зміненим промптом | Частина 3 |
| Порівняння двох прогонів | Частина 4 |
